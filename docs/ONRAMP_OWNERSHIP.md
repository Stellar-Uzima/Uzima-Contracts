# Excluded / On-Ramping Contract Ownership Map

The root `Cargo.toml` `workspace.exclude` list defers a subset of contract
crates ([issue #828](https://github.com/Stellar-Uzima/Uzima-Contracts/issues/828),
"Reintegrate 36 Excluded Contracts"). The manifest says *which* contracts are
excluded; it does not say **who** is bringing each one back, **what is
blocking** them, or **how far along** the work is. This map is the missing half:
one accountable owner and a progress status per excluded contract, so the
on-ramp backlog is trackable rather than a list of names.

The authoritative list of excluded paths is the root `Cargo.toml`
`workspace.exclude` array. The table below is generated from it and checked in
CI by [`scripts/check_onramp_ownership.py`](../scripts/check_onramp_ownership.py):
the script fails if a path is missing from the map, present in the map but no
longer excluded, duplicated, out of order, or missing a required field. Do not
edit the row set by hand — run `--write` to add newly excluded paths and drop
reintegrated ones.

## How to read the map

| Column | Meaning |
| --- | --- |
| **Excluded path** | The entry from `Cargo.toml` `workspace.exclude`. |
| **Contract** | The crate name, for quick scanning. |
| **Owner** | The reviewing team from [`.github/CODEOWNERS`](../.github/CODEOWNERS) that signs off on the on-ramp PR. |
| **Assignee** | The individual carrying the on-ramp. `unassigned` until the work is scheduled; **required** once status is `in-progress` or `reintegration-ready`. |
| **Blocker** | The concrete reason the contract is still excluded, or `—` when nothing is blocking it. |
| **Status** | Progress, from the vocabulary below. |
| **Target** | The issue or milestone the work is attached to. |
| **Last reviewed** | ISO date a maintainer last checked the row. Reviewed rows older than 90 days are flagged in triage. |

### Status vocabulary

| Status | Meaning |
| --- | --- |
| `not-started` | Recognised as excluded; no owner assigned yet. |
| `deferred` | Triaged and deliberately parked (see the `Cargo.toml` comment). |
| `blocked` | Someone investigated and hit a concrete wall recorded in **Blocker**. |
| `in-progress` | Actively being on-ramped by the named **Assignee**. |
| `reintegration-ready` | Compiles and tests green against the workspace pin; awaiting PR review. |
| `not-a-crate` | The path is not a crate root (no `Cargo.toml`), so it cannot be a workspace member. |
| `stale-entry` | The path no longer exists; it should be removed from `Cargo.toml` `exclude`. |

## On-ramp process

The three technical steps for removing a contract from `exclude` — workspace
SDK pin, `#![no_std]` cleanliness, and the three-test minimum — are defined in
[`docs/SYSTEM_ARCHITECTURE.md`](SYSTEM_ARCHITECTURE.md#excluded-contracts-audit-issue-828).
The ownership process on top of them is:

1. **Assign.** Pick an excluded path, move it to `in-progress`, and put your
   handle in **Assignee**. Keep one assignee per contract so accountability is
   unambiguous.
2. **Record the blocker.** If work stalls, set `blocked` and describe the wall
   in **Blocker** in enough detail that the next person can start from it.
3. **On-ramp.** Follow the three-step policy in `SYSTEM_ARCHITECTURE.md`, adding
   the `initialize` / happy-path / error-path tests it requires.
4. **Promote.** When the crate builds and tests pass against the workspace pin,
   set `reintegration-ready` before opening the PR.
5. **Reintegrate.** Remove the path from `Cargo.toml` `exclude` in the PR. On
   merge, run `--write`; the row disappears automatically because the path is no
   longer excluded.

Because the map is generated from the manifest, step 5 cannot leave a stale
row behind: the pull request that removes the `exclude` entry and the pull
request that regenerates the map are the same change.

### Review cadence

The map is reviewed in the issue-#828 triage pass, at minimum quarterly.
Maintainers bump **Last reviewed** on rows they re-confirm and re-assign
anything stale. The `check_onramp_ownership.py` gate runs whenever `Cargo.toml`,
the map, or the script changes, so a manifest edit that is not reflected in the
map fails CI immediately.

## Adoption notes

- **Seed run (2026-09-30).** The map was generated from the manifest with
  `python3 scripts/check_onramp_ownership.py --write`. It records every
  `workspace.exclude` entry, seeds **Owner** from the `contracts/*/` CODEOWNERS
  rule, and derives an initial **Blocker** from the crate's manifest: crates
  inheriting `soroban-sdk = { workspace = true }` are recorded as blocked by the
  workspace-resolution problem, and directories with no `Cargo.toml` are
  recorded as `not-a-crate`.
- **First stale entry caught.** `contracts/src` no longer exists on disk but is
  still in `workspace.exclude`. The map classifies it `stale-entry` with the
  blocker "path no longer exists; remove it from `Cargo.toml` `exclude`", which
  is the first concrete cleanup the map surfaces.
- **Reintegration.** When a contract is promoted out of `exclude`, the row is
  dropped on the same `--write` run; there is no separate bookkeeping to forget.
